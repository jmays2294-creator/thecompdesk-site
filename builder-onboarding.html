Builder Onboarding Guide

Get connected & build your first tile

This guide connects you to the Comp Desk Builder MCP from your own Claude / Claude Code / Cowork, so you can build calculators and skills that land in your private sandbox and flow into Joel's approval queue.

Nothing you build goes live without Joel's review.

1. Ground rules

  • You can build calculator tiles (a simple declarative spec, or — for advanced cases — a reviewed code tile) and Claude skills (.skill bundles).
  • Everything routes through Joel: draft → validate → submit → Joel approves → it publishes. Approved calculators appear in the Pro Workspace; approved skills go to the store catalog.
  • Never use real client, case, or injured-worker (PHI) data to build or test. Use only original, license-clean work. Your key is sandboxed: it cannot see production, PHI, the admin app, or any other builder's sandbox.
  • Your API key comes from Joel (admin → Builder API Keys). Treat it like a password.

2. Prerequisites

  • Claude Code or Cowork on your machine.
  • Your issued API key (looks like cdb_live_…).
  • A signed Contributor / IP agreement (Joel handles this before you start).

3. Connect the MCP

Add this to your MCP config (Claude Code: .mcp.json / Cowork: connectors):

{
  "mcpServers": {
    "comp-desk-builder": {
      "url": "https://admin.thecompdesk.com/mcp",
      "headers": { "Authorization": "Bearer cdb_live_YOUR_API_KEY" }
    }
  }
}

Verify the connection by asking Claude to run list_sandbox — you should get back your (initially empty) sandbox. To rotate a key, ask Joel to issue a new one and revoke the old; revocation is immediate.

4. Build a calculator (declarative — the default)

  1. get_calculator_template → returns a starter spec.
  2. Fill it in. Example — a temporary-total weekly rate tile: 
    {
  "name": "TT Weekly Rate",
  "slug": "tt-weekly-rate",
  "authoring": "declarative",
  "tier": "pro",
  "spec": {
    "inputs": [{ "key": "aww", "label": "Average Weekly Wage", "type": "number" }],
    "formula": "applyRateBounds(aww*2/3, doa)",
    "outputLabel": "Weekly TT rate"
  }
}
    Your formula may use the input keys, doa (date of accident), and the whitelisted calc-core helpers (see the contract). Anything else is rejected.
  3. create_calculator with that body → returns the draft (note its id).
  4. validate_build with { "spec": { …your spec… } } → fix any errors. Example rejection: formula calls non-whitelisted function: fetch.
  5. See it as a real tile before submitting. Ask Claude to run preview_calculator (it can pass your spec automatically). It returns a small HTML file — Claude can save it (e.g. tile-preview.html) and you just double-click it to open in your browser. You'll see the exact tile, with working inputs and a live result, rendered by the same engine the real Comp Desk workspace uses. Tweak the spec and re-preview until it looks right.
  6. When you're happy, tell Claude to submit it to the Comp Desk for approval — it runs submit_for_review with { "kind": "calculator", "ref_id": "<id>" }. It now sits in Joel's queue.

4b. Improve an existing calculator (don't start from scratch)

You don't have to build only brand-new tiles — you can improve what already exists (AWW/concurrent employment, SLU, LWEC, CCP, etc.). Two steps:

  1. Ask Claude to run get_reference. It lists every existing Comp Desk calculator, the calc-core function + statute behind each, and the canonical source URL (https://thecompdesk.com/js/calc-core.js). Example: Average Weekly Wage (global) → computeAWW, WCL §14 — includes §14(6) concurrent employment.
  2. Tell Claude what you want to improve (e.g. "I want to improve how concurrent employment is calculated"). Claude can read the canonical source to see exactly how it works today, then build your improved version — usually as a code tile (authoring: "code", which can call the CD.Calc helpers) — preview it, validate it, and submit_for_review with a note like "improved §14(6) concurrent AWW."

You can also fork an already-published tile: ask Claude to run list_published to see what's live, then fork_calculator with that tile's slug — it copies it into your sandbox as a fresh draft you can edit and resubmit.

One important distinction: a brand-new standalone tile, once Joel approves it, drops straight into the workspace. But a change to the shared math engine itself (like computeAWW, which feeds the app, website, and extension) doesn't auto-replace the live engine — Joel reviews your proposed improvement and, if approved, it's merged into calc-core behind the calculator regression suite before it goes live everywhere. Everything is gated to his approval either way.

5. Advanced: the code escape hatch

For tiles a formula can't express, set "authoring": "code" and provide code that receives (inputs, CD) and returns an object, e.g.:

return { weekly: CD.Calc.applyRateBounds(inputs.aww * 2 / 3, inputs.doa) }

Code tiles run only in Joel's CSP-locked sandbox during review (no network, no app/prod access) and go through a code diff. Use sparingly; prefer declarative.

6. Author a skill

  1. pull_skill_scaffold → returns a valid SKILL.md starting point.
  2. Edit the frontmatter (name kebab-case, a description ≥ 20 chars) and body.
  3. create_skill with { name, slug, skill_md }.
  4. validate_build with { "kind": "skill", "skill_md": "…" } → fix errors/warnings.
  5. submit_for_review with { "kind": "skill", "ref_id": "<id>" }.

7. Track your submission

get_review_status (optionally { "ref_id": "<id>" }) shows the state: submitted → changes_requested → approved/rejected → published. If Joel requests changes, update the draft (update_calculator / create_skill again) and submit_for_review once more.

8. REST quickstart (non-Claude tooling)

Same operations over HTTP. Base https://ltibymvlytodkemdeeox.supabase.co/functions/v1/builder-api:

KEY=cdb_live_YOUR_API_KEY
APIKEY=<project anon key, from Joel>
BASE=https://ltibymvlytodkemdeeox.supabase.co/functions/v1/builder-api

curl -s -X POST "$BASE/list_sandbox" -H "apikey: $APIKEY" -H "x-api-key: $KEY"
curl -s -X POST "$BASE/validate_build" -H "apikey: $APIKEY" -H "x-api-key: $KEY" \
  -H "content-type: application/json" \
  -d '{"spec":{"inputs":[{"key":"aww","type":"number"}],"formula":"applyRateBounds(aww*2/3, doa)"}}'
curl -s -X POST "$BASE/submit_for_review" -H "apikey: $APIKEY" -H "x-api-key: $KEY" \
  -H "content-type: application/json" -d '{"kind":"calculator","ref_id":"<id>"}'

9. Limits & etiquette

  • Rate limit: 120 requests / 60s per key (429 if exceeded).
  • Sandbox scope is absolute: your key only ever touches your drafts.
  • No PHI, no client data — ever. Original, license-clean work only.
  • Questions / a stuck submission → message Joel.
